# CartoAgent 长期优化完善计划

> 基于廖成《LLM-KG-Carto：一种基于大语言模型和知识图谱的自动制图框架》与艾廷华《DeepSeek驱动下的地图生成》两份样例，结合 CartoAgent 当前代码base，制定从原型到成品的全周期路线图。
>
> 制定日期：2026-08-17 | 维护人：CartoAgent 开发组

---

## 一、愿景与定位

**一句话定位**：集成大语言模型（LLM）与知识图谱（KG）的在线地图制图智能体——用户用自然语言描述制图需求，系统自动完成「需求理解 → 知识检索 → 任务规划 → 工具调度 → 数据获取 → 符号化渲染 → 整饰输出 → 质量校验」全链路，并支持类 QGIS/ArcGIS 的矢量编辑与交互式 refinement。

**终态目标（成品）**：
1. 自然语言一句话出图，覆盖行政区划图、交通图、水系图、专题统计图、地形晕渲图等主流图种。
2. 制图决策由知识图谱驱动，符号/投影/载负量/整饰符合制图规范，不违背制图常识。
3. 完整的交互式修改闭环：对话改图 + 手动编辑 + 样式面板，三者状态同步。
4. 多源数据自动融合：OSM + 本地精确数据 + 高德POI + DEM + 用户上传。
5. 探索 GeoToken / MapGPT 二轮驱动路线，为地图语言大模型预留接口。

## 三、技术路线总览

采用艾廷华提出的**双轮驱动**架构：

```
┌─────────────────────────────────────────────────────────┐
│                    一轮驱动（工程主线）                      │
│  LLM 嵌入地图制图链 + 知识图谱决策 + LangChain 工具生态      │
│  → 短期可落地，直接产出可用产品                              │
├─────────────────────────────────────────────────────────┤
│                    二轮驱动（研究探索）                      │
│  地图语言 Token化 → GeoToken 语料 → MapGPT 预训练           │
│  → 长期技术壁垒，为下一代地图生成奠基                        │
└─────────────────────────────────────────────────────────┘
```

一轮驱动对应廖成框架的完整实现：**LLM增强三法（微调/RAG/工具）+ 地图知识图谱 + 自动化制图框架**。
二轮驱动对应艾廷华方法2：**地图符号语言的LLM研发**，在 CartoAgent 中以实验模块形式并行推进。

### Phase 1：知识图谱深化与制图知识工程（第3-6周）

**目标**：对齐廖成的5大类本体，构建可推理的制图知识图谱，使制图决策从「硬编码」升级为「图谱驱动」。

#### 1.1 KG 本体扩展（P0）

在现有 `kg_ontology.py` 基础上补全5大类：

```
制图知识图谱本体
├── MapElement（地图元素）
│   ├── MainMap（主图）
│   ├── InsetMap（附图）
│   ├── MapDecoration（地图整饰）
│   │   ├── Title（图名）
│   │   ├── Legend（图例）
│   │   ├── ScaleBar（比例尺）
│   │   ├── NorthArrow（指北针）
│   │   ├── Chart（独立图表）
│   │   └── Annotation（附加文本）
│   ├── BaseLayer（基础图层）
│   ├── ThematicLayer（专题图层）
│   └── TerrainLayer（地形图层）
├── MapSymbol（地图符号）
│   ├── PointSymbol（点符号）
│   ├── LineSymbol（线符号）
│   ├── AreaSymbol（面符号）
│   ├── TextSymbol（文本符号：名称注记/说明注记/数字注记）
│   └── PictureSymbol（图片符号）
├── MapData（地图数据）
│   ├── NaturalGeoData（自然地理：水系/地貌/土质植被）
│   ├── SocioEcoData（社会经济：居民地/交通/境界政区）
│   └── DataType（栅格/点/线/面）
├── MapProjection（地图投影）
│   ├── ProjectionSurface（圆柱/圆锥/平面）
│   ├── DeformationProperty（等角/等积/任意）
│   └── ProjectionAxis（正轴/横轴/斜轴）
└── CartoFactor（制图影响因素）
    ├── LayoutSize（版面：A1/A2/A3/A4/B5…）
    ├── CartoRegion（制图区域：国家/省/市/县）
    ├── DisplayMedia（显示媒介：纸质印刷/电子屏幕）
    ├── MapTheme（地图主题）
    └── TargetAudience（目标受众：专家/学生/公众/老人/儿童）
```

**关系设计**：
- `MapTheme --requires--> MapData`（某主题需要哪些数据）
- `MapData --symbolized_by--> MapSymbol`（数据用什么符号）
- `CartoRegion --suitable_projection--> MapProjection`（区域适配投影）
- `MapTheme --affects--> CartoFactor`（主题影响因素）
- `MapSymbol --conflict_with--> MapSymbol`（符号冲突规则）

#### 1.2 制图规则库建设（P0）

将制图规范编码为图谱中的规则节点/约束关系：

| 规则类型 | 示例 |
|---------|------|
| 符号层级 | 水系面 > 道路线 > 注记（压盖顺序） |
| 颜色规范 | 水系=蓝色系、植被=绿色系、地貌=棕色系 |
| 注记规则 | 道路注记随线走向、面状注记居中、不压盖重要要素 |
| 投影选择 | 大范围→圆锥投影、城市级→高斯-克吕格/UTM、世界→圆柱 |
| 载负量 | 比例尺越小，要素抽稀比例越高 |
| 整饰规范 | 图名居中上方、图例右下/左下、比例尺下方、指北针右上 |

实现方式：在 `cartography_validator.py` 中新增规则引擎，从KG加载规则，对生成地图做约束校验。

#### 1.3 制图知识自动获取（P1）

参考廖成的「知识获取基本框架」：
- 从制图教材/规范文档（如《地图学》《国家基本比例尺地图图式》）中用LLM抽取实体和关系
- 批量导入Neo4j，扩充图谱节点
- 建立 `data/kg/carto_knowledge_base.jsonl` 知识源文件

#### 1.4 GraphRAG 增强（P1）

- 现有 `graphrag_service.py` 增加子图检索→接地生成链路
- 用户提问「绘制武汉市交通图需要哪些数据？」时，返回KG推理路径而非纯文本
- 前端 KGPanel 可视化展示推理路径（节点高亮+关系连线）

**里程碑**：KG节点≥800、关系≥2000；符号推荐可从KG推理得出；制图规则校验可运行。

### Phase 2：制图链完整化与工具生态（第7-12周）

**目标**：实现艾廷华「地图制图链中嵌入DeepSeek」的完整 DoMapAI 框架，打通从任务书到成图的全链路。

#### 2.1 六维制图任务理解（P0）

升级 `agent_service.py` 的意图识别，输出结构化任务书：

```json
{
  "theme": "交通图",
  "region": "武汉市",
  "spatiotemporal": {"time": "2025", "scale": "1:100000"},
  "method": "底色普染+线状符号",
  "audience": "公众",
  "symbol_preference": {"road": "深灰", "railway": "黑白段"}
}
```

- LLM 解析自然语言 → 六维结构化
- KG 校验六维合理性（如「交通图」是否需要「水系」作为底图）
- 缺失维度自动补全（如未指定受众→默认「公众」）

#### 2.2 多源数据融合调度（P0）

完善 `data_source_adapter.py`，实现统一数据获取层：

| 数据源 | 用途 | 优先级 |
|--------|------|--------|
| 本地精确GeoJSON | 武汉区县/水系/路网/POI | 1（最高） |
| OSM Overpass | 任意城市路网/水系/POI | 2 |
| DataV GeoAtlas | 全国行政区划边界 | 2 |
| 高德API | POI搜索/地理编码 | 3 |
| 天地图 | 影像底图/注记 | 3 |
| DEM (SRTM) | 等高线/晕渲 | 按需 |
| 用户上传 | 自定义数据（GeoJSON/SHP/CSV） | 1 |

- 数据获取策略：本地优先 → OSM兜底 → API补充
- 统一数据模型：所有来源转为标准GeoJSON + 属性schema
- 磁盘缓存 + 过期机制（现有 osm_service 已有，扩展到所有源）

#### 2.3 自动化符号推荐引擎（P0）

核心新模块 `symbol_recommender.py`：

```
输入：地图主题 + 要素类型 + 比例尺 + 受众
  ↓
KG查询：theme --requires--> data --symbolized_by--> symbol
  ↓
规则过滤：冲突检查、颜色规范、层级关系
  ↓
输出：符号配置（颜色/线型/线宽/填充/大小/注记字体）
```

- 内置符号库：交通/水系/地貌/植被/居民地/境界 六大类标准符号
- 支持用户自定义符号保存到KG
- 前端 StylePanel 展示推荐结果，可一键应用/微调

#### 2.4 地图整饰自动化（P1）

新模块 `map_decoration_service.py`：

| 整饰要素 | 自动策略 |
|---------|---------|
| 图名 | 自动生成「{区域}{主题}图」，居中上方，字体黑体 |
| 图例 | 根据图层符号自动生成，放置右下/左下（避开重要要素） |
| 比例尺 | 根据当前缩放级别计算，放置下方居中 |
| 指北针 | 右上角，可切换样式 |
| 附图 | 全国/全省位置示意图（小比例尺），放置左上角 |
| 文字说明 | 数据来源/制作时间/制图者，放置下方 |

- 整饰元素作为独立图层，可编辑/隐藏/拖拽
- 版面布局算法：检测地图空白区域，避免压盖

#### 2.5 LangChain 工具注册体系完善（P1）

现有 `tool_registry.py` 扩展为标准化工具生态：

| 工具类别 | 工具列表 |
|---------|---------|
| 数据获取 | fetch_boundary / fetch_road / fetch_water / fetch_poi / fetch_dem |
| 数据处理 | simplify_geometry / merge_features / clip_by_mask / reproject |
| 符号化 | apply_symbol / generate_legend / set_color_scheme |
| 整饰 | add_title / add_scalebar / add_north_arrow / add_inset |
| 分析 | buffer_analysis / overlay_analysis / density_analysis |
| 质检 | validate_topology / check_label_overlap / check_load |
| 导出 | export_geojson / export_svg / export_png / export_pdf |

- 每个工具：名称/描述/输入schema/输出schema/调用函数
- LLM 通过 function calling 自动选择和调用工具
- 工具调用链可追溯（前端展示执行步骤）

#### 2.6 交互式修改闭环（P1）

参考廖成「可视化信息反馈→配置信息查询融合→LLM配置修改→重新可视化」：

- 地图状态序列化：当前地图的完整配置（图层/符号/整饰）可导出为JSON
- 对话修改：用户说「把县道改成深灰色」→ LLM解析为配置diff → 应用 → 重新渲染
- 修改历史：每一步修改可撤销/重做/对比
- 前端展示：ChatPanel 中显示修改前后的配置diff

**里程碑**：六维任务解析可用；符号推荐引擎上线；整饰自动化覆盖5要素；工具生态≥15个工具。

### Phase 3：智能增强与质量闭环（第13-18周）

**目标**：提升制图专业性和智能化程度，建立质量反馈闭环。

#### 3.1 制图规范校验与质量评分（P0）

升级 `cartography_validator.py` + `quality_service.py`：

| 校验维度 | 检测内容 | 评分权重 |
|---------|---------|---------|
| 拓扑正确性 | 面重叠、线自交、悬挂节点 | 20% |
| 符号规范性 | 颜色是否符合色系、符号类型是否匹配要素 | 20% |
| 注记质量 | 压盖重要要素、注记遗漏、字体一致性 | 15% |
| 载负量 | 要素密度是否超限、LOD分级是否合理 | 15% |
| 投影合理性 | 区域与投影匹配度 | 10% |
| 整饰完整性 | 图名/图例/比例尺/指北针是否齐全 | 10% |
| 数据完整性 | 关键要素是否缺失 | 10% |

- 输出：质量分（0-100）+ 问题清单 + 修复建议
- 自动修复：简单问题（如缺少指北针）一键修复
- 前端：QualityPanel 展示评分雷达图 + 问题列表

#### 3.2 LLM 微调探索（P2）

参考廖成「领域书籍Lora进行模型微调」：
- 收集制图领域语料：教材、规范、论文、优秀地图作品描述
- 构建指令数据集：制图问答、符号推荐、任务解析
- LoRA 微调小模型（如 Qwen-7B / Llama-3-8B），增强制图语言风格
- 对比实验：微调前后制图任务解析准确率、符号推荐合理性
- 微调模型作为可选 Provider，与 DeepSeek 并行

#### 3.3 载负量智能优化（P1）

现有 `map-lod.js` 升级：
- 基于当前比例尺和地图尺寸，自动计算最佳要素密度
- 要素抽稀算法：Douglas-Peucker（线）+ 面积阈值（面）+ 距离阈值（点）
- 注记LOD：小比例尺只显示重要注记，大比例尺显示全部
- 前端可调节载负量滑块（简洁/标准/详细）

#### 3.4 多轮对话式 Refinement（P1）

- 上下文记忆：记住当前地图状态，支持连续修改
- 指代消解：「把它改成红色」→ 识别「它」指哪个图层/要素
- 批量操作：「所有道路都加粗」「水系统一用浅蓝色」
- 建议式交互：LLM 主动建议「这张图载负量偏高，是否抽稀？」

#### 3.5 地图风格迁移（P2）

- 预设风格包：经典/简约/复古/暗黑/学术/手绘
- 风格包 = 颜色方案 + 符号样式 + 字体 + 整饰风格
- 用户可保存自定义风格，分享/导入
- 基于参考图的风格提取（上传一张地图，提取其配色和符号风格）

**里程碑**：质量评分体系上线；LoRA微调实验完成；载负量自动优化；风格包≥5套。

### Phase 4：GeoToken 与地图语言模型探索（第19-26周，研究性并行）

**目标**：跟进艾廷华「地图符号语言的LLM研发」路线，在 CartoAgent 中搭建实验平台。

> 此阶段为研究探索，不影响一轮驱动的产品主线。以 experiments/ 目录为试验田，成熟后逐步迁移到主服务。

#### 4.1 地图语言 Token 化（P2）

完善 `geotoken_service.py`，实现三种Token化方案：

| Token化对象 | 方法 | 参考 |
|------------|------|------|
| 土地利用/面状数据 | 网格剖分 + SHDI多样性指数 + 主用地类型编码 | 艾廷华土地利用案例 |
| 等高线/线状数据 | 线段特征提取 + 线元序列化 | 艾廷华等高线案例 |
| 矢量要素集合 | 空间分形曲线（Hilbert/Morton）二维→一维序列化 | 艾廷华分形曲线方法 |

- 输出：统一的 GeoToken 序列格式
- 语料库构建：武汉全域数据 → Token化 → `data/geotoken_corpus/`

#### 4.2 预训练模型实验（P2）

- 等高线语言模型：基于BERT架构，768维向量，用武汉等高线语料预训练
- 土地利用模型：词嵌入（Word2Vec）+ 下游分类任务
- 实验框架：PyTorch + HuggingFace Transformers
- 评估：Token化重建精度、下游任务（地形内插/用地分类）性能

#### 4.3 GeoToken + GAN 地形生成（P3）

参考艾廷华「DEM 2 Map」+「虚实结合场景生成」：
- 从真实DEM提取地形结构线（山脊线/山谷线）
- 结构线 → GeoToken → GAN生成地形高程
- 交互控制：结构线重调（增/删/改走势）、竖向高程调整、噪声强度
- 应用：虚构地理场景生成（游戏/文创）、规划设计地形方案

#### 4.4 地图分析器/判读器/转换器（P3）

艾廷华提出的地图专业化LLM产品矩阵：
- 地图生成器（已有，持续优化）
- 地图分析器：自然语言查询地图中的空间模式（「武汉湖泊分布有什么规律？」）
- 地图判读器：上传地图图片，识别要素和主题（OCR + 视觉模型）
- 地图转换器：地图风格/格式/投影自动转换

**里程碑**：GeoToken三种方案均有demo；等高线预训练模型可运行；地形生成交互demo可用。

## 六、风险与依赖

| 风险 | 影响 | 应对 |
|------|------|------|
| LLM API 不稳定/限流 | 制图流程中断 | 多Provider降级 + 本地Ollama兜底 + 缓存常见查询 |

| 前端渲染性能瓶颈 | 大数据量卡顿 | WebGL迁移评估 + 要素抽稀 + 分片加载 |
| 制图知识获取成本高 | KG扩充慢 | LLM自动抽取 + 众包标注 + 从公开规范文档批量导入 |
| 一人开发精力有限 | 全周期过长 | 按优先级聚焦P0/P1，P2/P3按需推进 |
